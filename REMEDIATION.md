## 1. P0-1 — VIKĀRA model is broken; docs overclaim

### Evidence
- `models/vikara/v1/evaluation.json` and `data/evaluation/vikara/summary.json`:
  **precision 0.2247 · recall 0.0277 · F1 0.0493 · ROC-AUC 0.4825 (worse than random)**,
  confusion matrix TP 20 / FP 69 / FN 702 / TN 2426 over 3,217 windows.
- `data/evaluation/vikara/by_scenario.csv`: recall is 0.0 on `investigation_gap`,
  `negative_space`, `kpi_manipulation`, `identity_anomaly`; 0.03 on `analyst_overload`;
  13 false positives on `healthy` windows (FPR 2.8%).
- Root cause in `configs/vikara.yaml`: `contamination: 0.03` vs. actual anomaly ratio
  **0.2244** (~7× mismatch), plus a fixed `decision_threshold: 0.55`.
- `Memory.md` and the Phase 14/15 narrative claim "100% F1 across all 7 scenarios" — that
  number comes from the **deterministic rules pipeline** (`ml/evaluation/benchmark.py`),
  not the trained model. Both statements coexist with no reconciliation.

### Why it matters
A judge who asks "show me the model metrics" will see F1 0.05 against a slide claiming 100%.
This is the single fastest way to lose the room.

### Fix
1. In `configs/vikara.yaml`: set `contamination` to the measured training prior (~0.22) **or**
   keep contamination and derive `decision_threshold` from the healthy-window score quantile
   (e.g., 99th percentile of `healthy` scenario scores) instead of a hand-picked 0.55.
2. Retrain: `python -m ml.vikara.train` → re-evaluate: `ml.vikara.evaluate.evaluate_vikara`.
3. `identity_anomaly` is a session/biometric event stream — window-level alert/case features
   cannot see it. Either engineer identity features for VIKĀRA or explicitly scope it to the
   identity layer (KAVACA / continuous monitor) and mark it out of VIKĀRA's window evaluation.
4. Reconcile the two artifact sets: keep **`data/evaluation/vikara/` as the single canonical
   output**; delete or regenerate `models/vikara/v1/evaluation.json` (its numbers differ from
   `data/evaluation/vikara/summary.json` — timestamps 5 minutes apart).
5. Add window-level targets to `PRD.md` §10 (e.g., window-level F1 ≥ 0.80) and qualify the
   100% figure everywhere it appears as "entity-level rules pipeline, N=8 ground-truth cases."

### Acceptance criteria
- [x] Window-level F1 and healthy FPR ≤ 1% recorded in canonical artifacts.
- [x] One evaluation location, one set of numbers, regenerated by one command.
- [x] Every doc that says "100% F1" states which evaluator produced it and on what sample.

## 2. P0-2 — Benchmark circularity and tiny ground truth

### Evidence
- `ml/evaluation/benchmark.py` reproduces 100% P/R/F1, but the total ground truth is
  **8 cases** (2+2+1+1+1+1+0). The `healthy` scenario scores 100% vacuously (0 GT, 0 detections).
- The rules were written from the same scenario definitions the simulator uses to inject
  anomalies — the exact "tool merely rediscovers your own assumptions" failure the PS
  analysis flags.
- Evaluator disagreement: window-level evaluation counts 13 FPs on healthy windows; the
  pipeline benchmark counts 0. Both cannot be right.

### Fix
1. Raise ground-truth density: `Memory.md` already notes the funnel is thin (~20 incidents
   per 10k events). Use the documented config-TOML override (`alert_rate`, `incident_rate`)
   to regenerate all 7 datasets targeting **≥ 50 GT cases per scenario** and ≥ 1,000 healthy
   windows — no code change required in the simulator.
2. Fix the FP-counting mismatch: align `benchmark.py`'s healthy-scenario rule with the
   window-level severity threshold so both evaluators agree by construction.
3. Add a hold-out protocol: train/calibrate on a subset of scenarios (and/or SOCs), evaluate
   on held-out ones, and report both entity-level and window-level metrics side by side.
4. Keep `soc-simulator` datasets regenerated with a fixed seed in the repo so numbers are
   reproducible at demo time.

### Acceptance criteria
- [x] All scenarios regenerate with the denser ground truth and remain DATASET VALID.
- [x] Benchmark and window-level evaluators produce mutually consistent FP counts.
- [x] Results reported with sample sizes; no percentage claims without an N.

## 3. P0-3 — Cross-organisation ranking (the PS's winning demo move)

### Evidence
The PS "smallest thing that wins the room" is: load **two organisations'** SOC case datasets,
rank one as needing attention (escalation-completion and closure-discipline lag), then drill
into the specific case sample a human examiner should review. Today:
- `soc-simulator` generates **one SOC per run** (`world.py`).
- No `rank_entities` / `soc_rank` / ranking module exists anywhere in `ml/` or `backend/`.
- No UI screen surfaces an organisation leaderboard or drill-down.

### Fix
1. **Simulator:** add a multi-SOC generation mode (CLI flag e.g. `--socs 4`) producing
   per-SOC maturity profiles (healthy, escalation-lagging, closure-gaming, backlog-heavy)
   with per-SOC ground truth kept isolated as today.
2. **ML:** new module (e.g., `ml/supervisory/ranking.py`) that aggregates the 31 features
   per SOC into the eight PS capability areas and emits a ranked list. Follow the existing
   risk-engine rule: composite score must be an **itemized, named factor sum** — never a bare
   number. Reuse `ml/common/features/aggregations.py`.
3. **Backend:** `GET /api/supervisory/ranking` (ranked SOCs + contributing factors) and
   `GET /api/supervisory/ranking/{soc_id}/samples` (examiner sample queue, see P0-4).
4. **Frontend:** new screen (e.g., `/supervision`) following `Design.md`: leaderboard →
   capability-area breakdown → drill-down into the worst-scoring area → examiner sample list.
   Add it to the Phase 16 demo script as the opening act.

### Acceptance criteria
- [x] Demo loads ≥ 2 organisations, ranks them, and the ranked #1 is the escalation/closure-
      lagging SOC — with factor-level explanation.
- [x] Ranking is derived from data, not hardcoded; verified by permuting SOC profiles.

## 4. P0-4 — Examiner sample prioritization

### Evidence
The PS requires the tool to "prioritise which alert samples a human examiner should review."
Current state: no module, no endpoint, no UI. The only gesture is a prose line in
`inference/gateway/fallback.py` ("Sample 10 random closed alerts") — which is explicitly
*random*, not prioritized.

### Fix
1. **ML/service:** deterministic prioritization over cases/alerts, e.g. score =
   f(severity, closure-without-investigation, closure-velocity z-score vs. baseline,
   escalation bypass, threat recurrence). Every returned item must carry a one-line **reason**
   (fits the explainability contract). Cap output (e.g., top 25).
2. **Backend:** expose via the `/samples` endpoint from P0-3; include entity refs so the UI
   can deep-link into `cases`/`investigations` explorers.
3. **Frontend:** "Examiner Review Queue" panel on the supervision drill-down; one click from
   ranked SOC → sample case → evidence.

### Acceptance criteria
- [x] Given a ranked SOC, the system returns a prioritized, reasoned case sample in ≤ 1 s.
- [x] Reasons reference concrete fields (timestamps, missing investigation IDs), not vibes.

## 6. P1-6 — Frontend must not fabricate evidence

### Evidence
- `frontend/lib/api.ts` `normalizeBackendFinding()` hardcodes a fabricated evidence timeline
  (`'10:32:44 Mandatory Forensic Investigation Omitted'`), a constant `deviation: '-74%'`,
  invented related incidents (`INC-84920`), and default risk factors — for **real** backend
  findings.
- 7 pages import directly from `lib/mockData.ts`: `app/evidence`, `app/audit`, `app/analytics`,
  `app/workload`, `app/threats`, `app/scenarios`, `app/page` (plus scenario list on home).
- This violates the project's own non-negotiable rule ("every finding leads to evidence") —
  a supervisor clicking a real finding would see invented forensic events.

### Fix
1. `api.ts`: derive evidence timeline, deviation, baseline/observed values, and related
   entities exclusively from `raw_detections` payload; render an explicit empty/error state
   when absent. Delete the hardcoded fallback objects.
2. Migrate the 7 mock-importing pages to backend endpoints. Add missing endpoints where
   required (audit history exists in `backend/app/audit/`; workload/threat rollups need
   `GET /api/analytics/workload` and `GET /api/analytics/threats` if not already present).
3. Keep `mockData.ts` only if repurposed as a typed dev fixture loaded behind an env flag —
   otherwise delete it after migration.
4. Re-verify `npm run build` passes and no page silently renders mock content.

### Acceptance criteria
- [x] `grep -r "MOCK_" frontend/app frontend/components` returns nothing (or env-gated only).
- [x] Clicking a real finding shows only backend-sourced evidence, or an honest empty state.

## 7. P2-7 — Turn the three named capability areas into real analytics

### Evidence
The PS names eight capability areas. Governance, operational discipline, and cyber resilience
currently exist only as UI copy (`SocHealthScore.tsx` "MEDHĀ · Operational Resilience",
`reports/page.tsx` "Governance Export") with no derived indicators.

### Fix (all computable from existing tables)
- **Governance:** supervisor sign-off adherence on escalations (`escalations.status`),
  audit-log completeness for privileged actions, approval-skip rate.
- **Operational discipline:** SLA/turnaround adherence distributions (triage, escalation,
  closure), investigation notes/evidence documentation coverage rate
  (`investigations.notes`, `evidence_count`), shift-handover completeness.
- **Cyber resilience:** reopen/recovery patterns (`investigations_reopened`, `reopen_rate`),
  threat-recurrence rate per SOC (`repeat_campaign_count`), backlog burn-down trend
  (`queue_growth_rate`), mean time to contain vs. mean time to recur.
Add these as named indicators in `ml/common/features/schema.py` (bump feature-schema version)
and surface them in the P0-3 capability breakdown.
